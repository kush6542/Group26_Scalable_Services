1. PROBLEM DESCRIPTION & OBSERVED SYMPTOM (0.5 Marks)
----------------------------------------------------------------------
During initial multi-container deployment via Docker Compose, the complete
application failed to boot. While the PostgreSQL container reported a
state of 'Up (running)', all application microservices (restaurant_service,
payment_service, delivery_service, order_service) crashed immediately on
startup and entered a continuous restart loop (Exit code 1).

Clients attempting to hit http://localhost:8001/api/v1/orders/checkout
received 'HTTP 502 Bad Gateway' or 'Failed to connect to localhost port 8001'.

----------------------------------------------------------------------

----------------------------------------------------------------------

Root Cause Identification:
There is an asynchronous race condition between container lifecycle states:
Docker Compose's standard 'depends_on: [postgres]' directive only checks that
the PostgreSQL container's PID 1 process has been spawned (which takes ~0.2s).
However, PostgreSQL requires ~3.5 seconds to initialize its storage engine,
bind sockets, and execute '/docker-entrypoint-initdb.d/init.sql'.
The microservices started in 0.5s, attempted immediate SQLAlchemy schema
migrations against port 5432 before PostgreSQL was ready, received TCP
'Connection Refused', and crashed.

----------------------------------------------------------------------
3. SOLUTION & VALIDATION (1.0 Marks)
----------------------------------------------------------------------
To resolve this startup race condition deterministically without ad-hoc
'sleep' hacks, we introduced declarative health-checking readiness gates:

1. Added native PostgreSQL healthcheck in docker-compose.yml:
   postgres:
     healthcheck:
       test: ["CMD-SHELL", "pg_isready -U postgres -d postgres"]
       interval: 5s
       timeout: 5s
       retries: 10
       start_period: 10s

2. Updated all dependent microservices to use conditional health dependencies:
   restaurant_service:
     depends_on:
       postgres:
         condition: service_healthy

3. Configured Order Service (Saga Orchestrator) to gate on both postgres AND
   its downstream peer microservices:
   order_service:
     depends_on:
       postgres:
         condition: service_healthy
       restaurant_service:
         condition: service_healthy
       payment_service:
         condition: service_healthy
       delivery_service:
         condition: service_healthy
       notification_service:
         condition: service_healthy

Validation:
$ docker compose down -v
$ docker compose up --build -d
All containers started in strict topological readiness order.
$ docker compose ps
All 6 containers reported: STATUS = Up (healthy).

----------------------------------------------------------------------
4. LEARNING REFLECTION (0.5 Marks)
----------------------------------------------------------------------
This situated learning problem highlighted the fundamental difference between
'Process Liveness' (the OS process has started) and 'Application Readiness'
(the service is initialized and accepting network sockets).
In distributed container architectures, dependencies are asynchronous. Relying
on process start order is brittle. Production deployments must always implement
declarative readiness probes (such as Docker healthchecks or Kubernetes
readinessProbes) to coordinate multi-tier startup without race conditions.
